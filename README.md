## Overview

**IP Routing Analysis Using Wireshark** is a practical Computer Networks project that demonstrates how IP packets are routed from a Windows host to a remote destination.

The project combines **Wireshark** with built-in Windows networking utilities such as `ping`, `tracert`, `route print`, and `ipconfig` to examine:

- IP addressing and subnet configuration
- Default gateway selection
- Windows routing tables
- ICMP Echo Request and Echo Reply packets
- TTL (Time To Live) behavior
- Intermediate routers and network hops
- ICMP Time-to-Live Exceeded messages
- End-to-end connectivity

The experiment connects the theoretical concept of IP routing with real packet-level observations.

## How IP Routing Works

When a computer needs to send a packet to a destination, Windows checks its routing table.

If the destination belongs to the local network, the packet can be delivered directly through the local interface.

If the destination belongs to a remote network and no more specific route exists, Windows uses the **default route** and forwards the packet to the **default gateway**.

The router then makes its own forwarding decision and passes the packet toward the destination.

A simplified process is:

```text
Destination IP
      |
      v
Check Routing Table
      |
      v
Find Matching Route
      |
      v
Select Best Route
      |
      v
Use Gateway / Interface
      |
      v
Forward Packet
```

## Wireshark ICMP Analysis

The ICMP traffic generated by the ping was captured using Wireshark.

The captured packets included:

```text
192.168.1.186  ->  8.8.8.8
ICMP Echo Request

8.8.8.8  ->  192.168.1.186
ICMP Echo Reply
```

The packet capture showed an initial TTL of `128` on the outgoing Windows ICMP Echo Requests and a TTL of `118` on the received replies.

TTL is reduced by routers as an IP packet is forwarded. Therefore, the received TTL can provide information about the packet's journey through the network, although the original TTL chosen by the remote host must be considered when interpreting the value.

## 5. Trace the Route

The path to the destination was examined using:

*`tracert 8.8.8.8`*

The observed path contained seven hops:

```text
1.  192.168.1.1
2.  172.16.76.110
3.  Request timed out
4.  103.77.108.82
5.  142.251.76.31
6.  142.250.214.99
7.  8.8.8.8
```

### Hop Analysis

**Hop 1 — `192.168.1.1`**

This is the local default gateway.

**Hop 2 — `172.16.76.110`**

This is the next responding router encountered after the local gateway.

**Hop 3 — Request timed out**

The third hop did not respond to the traceroute probes. This does not necessarily mean that the router is down or that routing failed. Routers may be configured to ignore, filter, or rate-limit traceroute responses.

The later hops responded successfully, confirming that traffic continued beyond this point.

**Hop 4 — `103.77.108.82`**

This was the next responding network device shown by the traceroute.

**Hop 5 — `142.251.76.31`**

This hop belongs to the network path toward Google's infrastructure.

**Hop 6 — `142.250.214.99`**

Another responding hop in the path toward the destination.

**Hop 7 — `8.8.8.8`**

The final destination was reached successfully.

## 6. Analyze Traceroute Packets in Wireshark

The traceroute traffic was captured in Wireshark and filtered using:

*`icmp`*

The capture showed ICMP packets associated with the TTL-based route discovery process.

For example, the capture showed:

```text
192.168.1.186 -> 8.8.8.8
ICMP Echo Request
TTL = 1
```

followed by:

```text
192.168.1.1 -> 192.168.1.186
ICMP Time-to-Live Exceeded
```

This indicates that the first router encountered was:

```text
192.168.1.1
```

The capture also showed probes with:

```text
TTL = 2
```

followed by an ICMP Time-to-Live Exceeded response from:

```text
172.16.76.110
```

This identifies the second responding hop.

## TTL-Based Route Discovery

Traceroute works by progressively increasing the TTL of its probes.

Conceptually:

```text
TTL = 1
   |
   v
First router
   |
   v
ICMP Time-to-Live Exceeded
```

Then:

```text
TTL = 2
   |
   v
First router
   |
   v
Second router
   |
   v
ICMP Time-to-Live Exceeded
```

Then the TTL is increased again to discover the next hop.

The process continues until the destination is reached.

This allows the route between the source and destination to be reconstructed hop by hop.

## Correlation Between `tracert` and Wireshark

The two tools provide different views of the same routing process.

### `tracert`

Provides a human-readable list of responding hops:

```text
192.168.1.1
172.16.76.110
...
8.8.8.8
```

### Wireshark

Provides packet-level information such as:

- Source IP
- Destination IP
- ICMP type
- TTL
- Packet length
- Time-to-Live Exceeded responses

Therefore:

```text
tracert
   |
   | Human-readable route
   v
Network Hops

Wireshark
   |
   | Packet-level evidence
   v
ICMP + TTL + Responses
```

Together, they demonstrate how the route is discovered and how the packets are handled by intermediate routers.

## Conclusion

This experiment provided a practical understanding of IP routing and packet forwarding.

The Windows routing table showed how the host determines the appropriate route for a destination. Since `8.8.8.8` was outside the local `192.168.1.0/24` network, traffic was forwarded through the default gateway `192.168.1.1`.

The `tracert` command demonstrated that packets do not travel directly from the source to the destination. Instead, they pass through multiple intermediate routers. Wireshark provided packet-level evidence of this process by showing ICMP packets, TTL values, and ICMP Time-to-Live Exceeded responses.

Overall, the experiment successfully connected the theoretical concepts of **routing tables, default gateways, packet forwarding, TTL, ICMP, and traceroute** with real network traffic.
